## Step 1: Read the context

Read the progress log at {{PROGRESS_LOG}} before anything else. It records earlier
iterations: which findings were confirmed and fixed, and which were rejected and
why. The rejections are also listed below, so you need not reconstruct them.
## Standing rejections

These were reported in earlier iterations and dismissed with a reason. They are
the single biggest waste in a long run: half of every late iteration goes to
re-arguing questions already answered here.

{{LEDGER}}

Before reporting anything, check it against this list. If what you found is one
of these, you have three honest options and no fourth:
- drop it, because the recorded reason holds;
- report it anyway with its id in the line's opening token, saying what the
  recorded reason gets wrong;
- report it with its id because the code has changed since it was rejected.

Never report one of these as if it were new. Naming the id is what lets rrev
count a recurrence instead of opening a second entry for the same argument.


Then get the branch context:

## Step 2: Launch every reviewer agent

{{AGENTS: conformance, tasks, quality, implementation, testing, simplification, documentation}}

Do not proceed to step 3 until every agent has returned its report.

Do not embed code or diffs in the agent prompts. Each definition tells its agent
how to obtain the diff itself; pasting a diff into seven prompts is slow and buys
nothing.

## Step 3: Deduplicate, verify, fix

### 3.1 Deduplicate
Merge findings that name the same file:line and the same issue, keeping every
reporting agent's name on the merged finding.

### 3.2 Verify every finding against the real code
For each finding, open the cited location, read the surrounding context, and
decide:
- CONFIRMED - the issue is real and not already mitigated elsewhere
- REJECTED - it does not exist, is already handled, or the agent misread the code

A conformance verdict is verified the same way: check the cited line, or run the
search yourself before accepting that a requirement is unimplemented.

Reject nothing for being pre-existing. A defect the branch touches is in scope
whether this branch introduced it or not.

### 3.3 Fix what you confirmed
Unless the run mode above forbids changing the repository, fix every confirmed
finding, then validate and commit:
- Run the validation command: {{VALIDATION_COMMAND}}
  If that reads "(not configured)", run the project's own test and lint commands
  as its CLAUDE.md, README, or Makefile define them.
- All tests must pass and all lint issues must be resolved before you commit.
- Commit with: `git commit -m "fix: address review findings"`

## Step 4: Report

Report every verified finding, one per line, in this form so rrev can collect
them:

FINDING: <critical|major|minor> | <file>:<line> | <agent> | <requirement or -> | <summary>

Report each rejection the same way, so the next iteration does not re-litigate it:

REJECTED: <file>:<line> | <agent> | <what was claimed> | <why it is not a real finding>

Re-raising something from the standing-rejection list? Put its id in the opening
token: `FINDING[R7]:` or `REJECTED[R7]:`. Leave the token bare for anything new.


Report the validation command's outcome once, so the progress log records
whether the fixes were validated:

VALIDATION: <pass|fail> | <the command you ran> | <what failed, or ->

## Signal contract

A signal is a marker rrev reads back from your output. It counts only when it is
alone on its own line and outside any code fence, so quoting one inside a fenced
block does nothing.

- <<<RREV:REVIEW_DONE>>> - emit only when this iteration confirmed zero findings
  and you changed nothing. It means "this review found nothing", never "I finished
  fixing things".
- <<<RREV:TASK_FAILED>>> - emit when you cannot proceed at all. The run stops and
  reports this phase.

Emitting no marker is not success. rrev reads a missing marker as "work was done,
iterate again" and runs this phase again, up to {{MAX_ITERATIONS}} iterations. So
when you fixed and committed something, emit nothing: the next iteration has to
check whether your fixes broke anything.

OUTPUT FORMAT: no markdown formatting. Plain text and - lists are fine.
